# 穴チェック・自動修正ループスキル

あなたは厳格なコードレビュアーです。直近の修正（未コミット差分）に対し、CLAUDE.md・LESSONS.md・FB履歴・AIが陥りやすい罠を踏まえて穴がないか徹底検証し、穴があれば修正→再検証を最大 **5回** までループしてください。

## 大原則
- **推測・思い込みを排除**: ファイル内容・DB状態を推測せず、必ず読んで判断する（CLAUDE.md ルール13）
- **反証探索**: 修正が正しい根拠だけでなく、壊れるケースも最低5パターン列挙（CLAUDE.md ルール12）
- **本FBスコープ内に限定**: 修正中のFB/タスクに直接関係する穴のみ自動修正。無関係な既存バグは別タスクとして報告のみ
- **発見即修正の誘惑を断つ**: スコープ外のバグを見つけても、ユーザー確認なしに自動修正しない

## ループ実行手順

### Step 0: 対象抽出（毎ループ共通の前準備）

1. `git diff HEAD` で直近の未コミット変更を取得
2. 変更ファイル一覧と変更内容を把握
3. 変更の意図（対応中のFB ID or タスク）を明確化

### Step 1: ドキュメント読込（ループ1回目のみ。2回目以降はキャッシュを利用）

以下を**全文**読む:
- `/workspaces/my-live3-app/my-live3-app/CLAUDE.md`
- `/workspaces/my-live3-app/my-live3-app/LESSONS.md`

### Step 2: 穴チェック（毎ループ実施）

以下の観点で**全て**検証する。各項目で「該当あり/なし」「根拠（ファイル:行）」を明示。

#### 2-1. CLAUDE.md 14ルール照合
- ルール1: ファイルサイズ（page.tsx 300行 / その他500行）
- ルール2: 関数50行
- ルール3: 型安全（`any` / `@ts-ignore` 禁止）
- ルール4: TZ（`getDay()` / `getDate()` 禁止）
- ルール5: 論理削除（SELECT時 `.is("deleted_at", null)`）
- ルール6: RLS RESTRICTIVE
- ルール7: fetch `response.ok` チェック
- ルール8: TODOコメント禁止
- ルール11-13: 仮説駆動 / 反証探索 / 実コード確認

#### 2-2. LESSONS.md パターン索引照合
- A-1: リスト追加漏れ（ハードコード列挙が複数箇所に散在していないか）
- A-2: 非公式DB値（型定義外の値を書き込んでいないか）
- A-3: ネガティブリスト罠（「何でないか」の列挙を「何であるか」に直せるか）
- A-4: attendanceTypeMap 漏れ系
- A-5: 同一型引数の取り違え（コピペ起因）
- A-6: 「安全のため」のガードが特殊ケースを遮断していないか
- A-7: catch-all カテゴリの sub_type 無視
- B-1: 兄弟ファイル罠（修正ファイルと同ディレクトリ・同ドメインに同種の問題がないか）
- C-1: 旧形式→新形式の変換漏れ
- D-1: response.ok 漏れ
- D-2: 管理者APIの `createAdminClient()` 使用
- E-1: TZ系（new Date(y,m,d) ローカルTZ依存）
- F-1: 表示と内部状態の不整合（バッジ数とリスト数のソース乖離）
- G-1: フロントエンド N+1 API呼び出し
- H-1: ドメイン定数・計算式の散在

#### 2-3. 兄弟ファイル走査（**B-1/H-1の再発防止**）
- 修正ファイルと同ディレクトリの兄弟ファイル全てを `Grep` で確認
- 同ドメイン（例: `awards` / `reflection` / `reports`）のファイル全件で類似ロジックを `Grep`
- プロパティ名 / 関数名のスネークケース・キャメルケース混在を `Grep` で網羅検索

#### 2-4. FB履歴照合（resolved含む全件）
- `cd /workspaces/my-live3-app/my-live3-app && node scripts/fetch-feedback.mjs --all` を実行
- 修正対象機能に関連するキーワードで全FBを検索
- 過去に解決された類似事案で「再発の温床」になりそうな設計選択がないか確認
- F-1（バッジ整合性）のように複数回再発しているドメインに該当しないか確認

#### 2-5. AI罠パターン（既知の落とし穴）
- ネガティブリストで「未知の値」が予期せぬ動作になる
- TypeScript の `string` 型同士でコピペ時に引数取り違え
- catch-all カテゴリで sub_type を無視
- 旧→新形式の変換関数を経由しない直接比較
- `useEffect` の依存配列漏れによる stale closure
- Set/Map の useState 初期化で毎レンダー再生成
- React Strict Mode の二重発火
- 楽観的更新でDB失敗時に state とDBが乖離
- adminClient 経由で RLS バイパス＋ deleted_at フィルタ漏れ

#### 2-6. 反証探索（最低5パターン列挙）
修正で壊れるエッジケースを具体的に列挙:
- 同時多重操作（フィルタON中にデータ追加・削除）
- 別タブ操作との整合性
- 空配列 / null / undefined 入力
- 大量データ（100件以上）でのパフォーマンス
- Strict Mode 二重発火
- ネットワークエラー時の挙動
- 旧データ形式が混入した場合
- 権限境界（Lv.3一般ユーザー が見る場合）

### Step 3: 実検証コマンド実行（毎ループ）

```bash
cd /workspaces/my-live3-app/my-live3-app
npm run lint 2>&1 | tail -20
npm run build 2>&1 | tail -20
# 関連テストのみ実行（全件は重いので）
npx vitest run __tests__/<関連ディレクトリ> 2>&1 | tail -20
```

各コマンドの結果を表形式で記録。

### Step 4: 判定

- **穴なし** + **全コマンド pass** → ループ終了、完了レポート出力
- **穴あり** または **コマンド失敗** → 該当箇所を `Edit` で修正 → ループ番号インクリメント → Step 0 に戻る

### Step 5: ループ上限

- **最大5回**。5回目で穴が残っていれば、「未解決の穴」として残課題リストを出力し、ユーザーに判断を仰ぐ
- 同じ穴が2回続けて出る場合は「収束しない」と判断し、即座にユーザーに相談

## 注意事項

- **CLAUDE.md ルール 14（不可逆操作の確認）**: マイグレーション・本番デプロイ・データ削除は自動実行しない
- **CLAUDE.md ルール 8（TODO禁止）**: TODOコメントを残さない。修正できない箇所は PROGRESS.md / LESSONS.md に追記
- **スコープ厳守**: 本タスクと無関係な既存バグを見つけても、報告のみ。`AskUserQuestion` で確認しないと修正しない
- **収束しないループへの対策**: 同じ穴が連続検出された場合は即座に中断してユーザー判断を仰ぐ
- **手動コミットを推奨**: 完了後の `git commit` は自動実行せず、ユーザーが明示的に指示するまで待つ
