# /intent — 作る前に、意図を1枚にする

会話の中にしかない「やりたいこと」は、会話を閉じたら消える。ファイルにしておけば、別の会話・別の人・レビュー担当のAIが同じ意図で動ける（公式: Claude Academy「AI-Native SDLC Playbook」）。この1枚が、あとで `/ship` のレビューの**採点基準**になる。

## いつ使うか

次のどれかに当たる作業は、実装の前に作る。当たらない小さな修正（文言・表示崩れ等）は不要で、PR 本文で足りる。
- migration がある（本番 DB の形が変わる）
- 社外に届くものを変える（購入者あてメール・受注/出荷データの外部連携・帳票）
- 新しい機能・画面

## 進め方

1. 依頼者（FB を受けた人）にインタビューする。**質問は1回に1つ**。答えがあいまいなら、例を3つ出して選んでもらう。
2. FB が起点なら、先にそのご意見の本文・やり取り・添付を全部読む（推測で埋めない）。数字が絡むなら実データで数える（CLAUDE.md 絶対ルール12）。
3. 下の項目が全部埋まったら `docs/intents/<YYYY-MM-DD>-<英小文字とハイフンの短い名前>.md` に保存する。
4. 依頼者に読んでもらい、「違う」と言われたところだけ直す。

## ファイルの形

```markdown
> このファイルをもとに作業するAIへ: 出来上がったら、下の項目と見比べて、合っているかを確かめてから報告すること。

# <何を作るか（1行）>

- 起点: <FB の ID・依頼者・日付>
- 書いた人: <名前>（インタビュー: Claude）

## 1. 何に困っているか
<誰が・どの画面で・何をしようとして・何が起きるか。現場の言葉のまま>

## 2. どうなったら嬉しいか
<操作 → 結果の形で。「○○を押すと△△が出る」>

## 3. 誰に関係するか
<購入者（フロント・スマホ/PC）／店舗運営者（管理画面）／取引先・外部連携（社外）。画面と人の両方>

## 4. 守らないといけない条件
<例: 既存の受注データを消さない／購入者に飛ぶメール文面は変えない／在庫数がマイナスにならない／本体（src/Eccube/）は直接編集しない>

## 5. まだ決まっていないこと
<決めるのは誰か・いつまでか。決まっていないまま作ってよい部分と、止まる部分を分ける>

## 6. 本番への影響
- migration: あり／なし（ありなら、表・列の追加だけか、削除・名前変更があるか）
- 社外に届くもの: 変わる／変わらない（変わるなら、実物の文面をどこで確かめるか）

## 7. 完了の確かめ方（数えられる形で）
- [ ] <例: 商品ID 12 の商品詳細ページに送料無料バッジが出る>
- [ ] <例: 受注一覧の CSV 出力件数と画面の件数の差が0件>
```

## 注意

- 「いい感じに」「わかりやすく」は確かめられない。**7. は数えられる形**（件数・値・あるかないか）にする。
- 解決策を先に書かない。1〜5 は困りごとと条件だけ。どう作るかは実装する側が決める（公式: 目的・ガードレール・終了条件だけを渡す）。
