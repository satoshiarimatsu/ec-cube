# /ship — 本番に出すルール（1本）

本番に出るのは「CI（lint-test-build）と本番 DB への migration（migrate）が緑の版」だけ（Vercel の Deployment Checks がこの2つを待つ）。このスキルは、その門を**手元で先に**通してから PR を出すためのもの。ルールの正本は `docs/onboarding.md`「本番に出すルール」。

**終わりの条件**: ①ship-check が全部緑で受領証が出た ②別文脈レビューの指摘が0件、または全件に「直した／直さない理由」を書いた ③PR を出した ④マージ後なら main の CI と本番反映を確認した ⑤報告に「何を操作すると何が起きるか」がある。①が5回やっても緑にならなければ止めて、赤の内容を報告する。

## 0. 前提をそろえる

- いまのブランチが `main` ではないこと（main 上の編集・commit・push は hooks が止める）。
- `git fetch origin` → `git merge origin/main` で最新を取り込む。
- **同じ件を誰かが先にやっていないか**: `gh pr list --state open` と `git ls-remote --heads origin` を見る（LESSON E-61: 未マージのブランチは main に無いので、main だけ見ても見つからない）。

## 1. intent と見比べる

`docs/intents/` に今回の件のファイルがあれば読み、項目（困りごと／どうなったら嬉しいか／誰に関係するか／守る条件／未決事項／本番への影響）と**完了の確かめ方**を、1つずつ実装と突き合わせて「満たした／満たしていない（理由）」を列挙する。

intent が無い場合、次のどれかに当たるなら先に `/intent` で作る（当たらなければ不要）: migration がある／社外（書店様・本部シート）に届くものを変える／新しい機能・画面。

## 2. ship-check（CI と同じ検査を手元で）

```bash
cd my-app && npx tsx scripts/ship-check.ts
```

- ci.yml の `lint-test-build` の `run:` を**全部**そのまま回す（人が選ばない → LESSON C-14）。ビルド込みで約7分。
- 赤が出たら直してコミット → 回し直す。**全部緑・未コミット無し**のときだけ受領証が出る。受領証が無い版では `gh pr create` を hooks が止める（受領証のあとにドキュメントだけ直した場合は通る）。
- migration を足したなら、「Guard migration release safety」が削除系（DROP COLUMN 等）を止める。止まったら表示に従う（読み手を消す PR を先に本番へ出し、migration は別 PR で申告付き → LESSON C-28）。
- 関数・ビューを作り直す migration は、**直前の定義**（このリポジトリで最後にその関数・ビューを作った migration）を写し元にする。CI の「Guard migration redefinitions do not silently drop code」が、前の定義から消えた中身を数えて止める（A-16）。2026-10-07 から本番を変える経路は CI の1本なので、直前の定義＝本番の定義（同日69件全件一致を実測）。本番を読む必要は無い。

## 3. 別の文脈のAIにレビューさせる

作った会話の中で見直すより、**作った経緯を知らないAIに基準だけで見させる**ほうが見落としが減る（公式 best practices）。Agent ツールで general-purpose のエージェントを1体立て、次をそのまま渡す。

```
これは外注さんが書いてきた変更です。本番に出す前に、厳しめにチェックしてください。
作った経緯は知らなくて大丈夫です。下の材料と基準だけで見てください。

■ 材料
- 変更: `git diff origin/main...HEAD` を自分で実行して読む（リポジトリ: <パス>）
- 意図: <docs/intents/... のパス。無ければ PR 本文の「何が起きていたか」>
- 基準: CLAUDE.md の「6パターン穴探し」「SST固有のドメイン観点」、LESSONS.md 末尾の索引のうち変更に関係するカテゴリ

■ 必ず見る観点
1. 値の意味を広げた／変えたなら、読む側を grep で全部数えたか（A-11 / E-49）
2. 新しい列・経路を足したなら、同じ役割の既存の列・経路が無いか（E-20 / E-61）
3. 社外に届くもの（メール本文・ヘッダ・シート）が変わるなら、実物の文面（E-15 / E-27）
4. 取得失敗を「空」「0件」に潰していないか（D-14）
5. migration があるなら、RLS・論理削除・部分ユニーク・本番の実定義から写したか（A-2 / A-13 / A-16）
6. 意図に書かれた「守る条件」を破っていないか

■ 出し方
- 問題は小さいものも含めて全部出す（絞るのはこちらでやる）。
- 1件ずつ「ファイル:行／何が起きるか（具体的な入力→結果）／どう直すか」。
- 推測は「推測」と書き、確かめた事実と分ける。
```

返ってきた指摘は、直すか、直さない理由を書く。結果は PR 本文の「別文脈レビュー」に貼る。直したら 2 から回し直す。

## 4. PR を出す

`.github/pull_request_template.md` の見出しをすべて埋める。特に:
- **本番に出る順番**: migration の有無。削除系があるなら申告の行と、先に出した PR 番号。
- **現場向けの説明**: 毎朝「アプリの更新情報」（PDF と文章）としてメンバーにそのまま配られる（M57）。使う人の言葉で、1つの変更につき `### 見出し` ＋「分類／場所／前は／今は」を書く（書き方はテンプレートのコメント）。画面に出る文字は実際のコードから写す（推測で書かない）。画面や動きが変わらない PR は「なし」とだけ書く。空のままにすると、更新情報に「説明が書かれていない変更」として題名だけが載る。
- **開発者向けの要点**: GitHub のトップ（README）の「最近追加された機能」に毎朝そのまま載る（M88）。「何ができるようになったか／どこにあるか／触るときの注意」を1行ずつ。機能が変わらない PR は「なし」とだけ書く（空のまま出すとコードの PR は「要点未記入」として題名だけ載る）。
- **異常系5件**: 「○○のとき → コードの○○分岐 → 期待動作」の形（CLAUDE.md 実装後セルフチェック）。
- **実機確認**: 人が確認すること。緑の条件には含めない（機械では判定できない）。

## 5. マージ後の見張り

マージしたら、次を確かめるまでが仕事。
- main の CI: `gh run list --branch main --workflow ci.yml --limit 3`。`lint-test-build` と `migrate` の両方が緑か（`gh api .../commits/<sha>/status` の緑は Vercel だけで CI ではない → C-29）。
- migration を含むなら: `migrate` のログに適用したファイルが出ているか。さらに本番に**オブジェクトが実在するか**（一覧の「適用済み」ではなく → E-42）。型の差分 PR が自動で出ていたら中身を見てマージ。
- 本番反映: Vercel が本番へ昇格したこと。
- 赤なら**その日のうちに直す**。main が赤のままだと、以降の変更が誰のものも本番に出ない。

## 6. 報告

CLAUDE.md「完了の定義」⑤の形で、**何を操作すると何が起きるか**を手順で書く。ご意見（FB）起点なら、スレッドへの返信に修正内容そのものを書く。
